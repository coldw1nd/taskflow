# Требования к данным и схема TaskFlow

## Требования к хранению и доступу

| Объект | Состав данных | Источник / потребитель | Ограничения и доступ |
|---|---|---|---|
| `users` | id, email, password_hash, created_at | Регистрация и вход; сервис аутентификации | Email уникален и нормализуется к нижнему регистру; хеш пароля не выдаётся клиенту |
| `tasks` | id, title, status, deadline, created_at, completed_at, user_id | Формы задач, список и фильтры; API задач | Владелец обязателен; title 1–200 символов; статус active/completed; дедлайн не раньше создания |
| `tags` | id, name, user_id | Форма тегов и фильтр списка; API тегов | Имя 1–50 символов; UNIQUE(name, user_id) |
| `task_tags` | task_id, tag_id | Назначение тегов задаче; формирование списка | Составной PK исключает дубли; оба FK с ON DELETE CASCADE |
| `audit_logs` | id, user_id, action, entity_type, entity_id, created_at, details_json | Сервисный слой; аудит и отладка | Технический журнал; пользовательские секреты не записываются; user_id обнуляется при удалении пользователя |
| `schema_migrations` | version, applied_at | Механизм миграций | Одна строка на применённый SQL-файл |

## Связи и нормализация

- `users` → `tasks`: один пользователь имеет много задач (1:M).
- `users` → `tags`: один пользователь имеет много тегов (1:M).
- `tasks` ↔ `tags`: связь многие-ко-многим реализована через `task_tags`.
- Данные пользователя, задачи и тега хранятся раздельно; таблица связи не дублирует описательные атрибуты.
- Схема близка к третьей нормальной форме: свойства каждой сущности хранятся в своей таблице, а связи M:M вынесены в отдельную таблицу.

## Ограничения целостности и индексы

| Ограничение / индекс | Назначение |
|---|---|
| `PRIMARY KEY` в основных таблицах | Уникальная идентификация строк |
| `UNIQUE(email)` | Запрет повторной регистрации с тем же email |
| `UNIQUE(name, user_id)` | Уникальность имени тега в пределах пользователя |
| `CHECK(length(title) > 0 AND length(title) <= 200)` | Допустимая длина названия задачи |
| `CHECK(status IN ('active', 'completed'))` | Допустимые статусы задачи |
| `CHECK(deadline IS NULL OR deadline >= created_at)` | Дедлайн не может быть раньше создания |
| `FOREIGN KEY ... ON DELETE CASCADE` | Удаление связанных task_tags вместе с задачей или тегом |
| `idx_tasks_user_created_id` | Список задач пользователя с сортировкой по дате |
| `idx_tasks_user_status_created_id` | Фильтрация задач пользователя по статусу и сортировка |
| `idx_task_tags_tag_task` | Обратный поиск связей по тегу |
| `idx_audit_logs_user_created` | Получение истории действий пользователя |

## Версионирование

DDL разнесён по файлам `migrations/001_core.sql`, `002_audit_log.sql`, `003_query_indexes.sql`. Таблица `schema_migrations` хранит имена и время применения файлов, а `schema_migration_reverts` — историю явных откатов. Откат не приводит к автоматическому повторному применению этой миграции при следующем запуске приложения. Миграции выполняются в транзакции и запускаются при инициализации БД. Существующие таблицы создаются через `IF NOT EXISTS`, поэтому исходная база TaskFlow сохраняет текущие записи при добавлении журнала и индексов.

Файл `sql/queries.sql` содержит примеры DML для чтения, фильтрации, создания, изменения и удаления задач. В реальном приложении аналогичные операции выполняются через подготовленные запросы better-sqlite3.

## Проверка БД

`npm run db:check` выполняет `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, показывает применённые миграции и индексы, а также выводит `EXPLAIN QUERY PLAN` для запроса списка задач. Набор `tests/database.test.js` проверяет миграции, индексы, ограничения CHECK/UNIQUE/FK, каскадное удаление и целостность SQLite.
