# Анализ требований и варианты использования TaskFlow

## Назначение продукта

TaskFlow — веб-приложение для ведения личного списка задач. Пользователь регистрируется, входит в систему, создаёт задачи, указывает срок выполнения, отмечает завершение, удаляет задачи и группирует их тегами.

## Требования

### Функциональные

1. Регистрация и вход пользователя по адресу электронной почты и паролю с выдачей JWT.
2. Создание, просмотр, изменение и удаление собственных задач.
3. Изменение статуса задачи между `active` и `completed`.
4. Указание необязательного срока выполнения и отображение просроченных задач.
5. Создание и удаление собственных тегов.
6. Привязка одного или нескольких тегов к задаче.
7. Фильтрация списка по статусу и тегу, постраничная выдача.
8. Получение данных текущей учётной записи и проверка работоспособности API.

### Нефункциональные

- Безопасность: хеширование паролей, валидация входа, параметризованные SQL-запросы, защита от XSS, проверка владения объектом (IDOR/BOLA).
- Производительность: ориентир для типовых операций чтения — ответ до 2 секунд; индексы на полях фильтрации, связи и сортировки.
- Надёжность: транзакции для операций, изменяющих задачу и набор её тегов; проверка целостности БД.
- Поддерживаемость: единый JSON-формат ответов и ошибок, OpenAPI-спецификация, автоматические тесты и CI.

### Ограничения

- Учебный MVP реализован как монолит на Node.js и Express.
- Для хранения используется SQLite; отдельный сервер СУБД не требуется.
- Публичное production-развёртывание не входит в текущую локальную проверку и остаётся отдельным этапом.

## Акторы и варианты использования

| Актор | Варианты использования |
|---|---|
| Гость | Регистрация; вход в систему |
| Авторизованный пользователь | Просмотр своих задач; создание задачи; изменение задачи и статуса; удаление задачи; просмотр тегов; создание/удаление тега; назначение тегов; фильтрация и пагинация |

## Текстовые сценарии

### UC-01. Регистрация

**Основной актор:** гость. **Предусловие:** учётная запись с указанным email отсутствует.

1. Гость открывает форму регистрации.
2. Вводит email и пароль длиной не менее 8 символов.
3. Клиент отправляет `POST /api/auth/register`.
4. Сервер проверяет входные данные, проверяет уникальность email и сохраняет хеш пароля.
5. Сервер возвращает `201 Created` и публичные данные пользователя без хеша пароля.

**Альтернативы:** некорректные данные — `400`; email занят — `409`.

### UC-02. Вход

**Основной актор:** зарегистрированный пользователь. **Предусловие:** учётная запись существует.

1. Пользователь вводит email и пароль.
2. Клиент отправляет `POST /api/auth/login`.
3. Сервер сравнивает пароль с сохранённым bcrypt-хешем.
4. При совпадении сервер выдаёт JWT; клиент сохраняет токен и использует его в `Authorization: Bearer`.

**Альтернатива:** неверные учётные данные — `401`; слишком частые попытки — `429`.

### UC-03. Создание задачи

**Основной актор:** авторизованный пользователь. **Предусловие:** пользователь вошёл в систему.

1. Пользователь вводит название, при необходимости срок и выбирает теги.
2. Клиент отправляет `POST /api/tasks` с JWT.
3. Сервер валидирует название и срок, проверяет принадлежность тегов пользователю.
4. В транзакции создаётся задача и связи с тегами.
5. Сервер возвращает `201 Created` с объектом задачи и массивом тегов.

**Альтернативы:** ошибка валидации — `400`; отсутствующий/чужой тег — `400`; отсутствующий токен — `401`.

### UC-04. Просмотр и фильтрация задач

**Основной актор:** авторизованный пользователь. **Предусловие:** пользователь вошёл в систему.

1. Клиент запрашивает `GET /api/tasks`.
2. При необходимости передаёт `status`, `tag_id`, `page` и `limit`.
3. Сервер выбирает записи только с `user_id` текущего пользователя и возвращает `items`, `page`, `limit`, `total`.

**Альтернатива:** некорректные параметры — `400`; отсутствующий токен — `401`.

### UC-05. Изменение статуса задачи

**Основной актор:** авторизованный пользователь. **Предусловие:** задача принадлежит пользователю.

1. Пользователь отмечает задачу выполненной или возвращает её в активный список.
2. Клиент отправляет `PATCH /api/tasks/{id}` с полем `status`.
3. Сервер проверяет владение задачей и допустимое значение статуса.
4. При завершении заполняется `completed_at`, при возврате в активный статус поле очищается.
5. Сервер возвращает обновлённую задачу.

**Альтернатива:** задача не найдена или принадлежит другому пользователю — `404`.

### UC-06. Управление тегами

**Основной актор:** авторизованный пользователь.

1. Пользователь создаёт тег через `POST /api/tags`.
2. Для назначения набора тегов задаче клиент отправляет `PUT /api/tasks/{id}/tags` с `tagIds`.
3. Сервер проверяет владельца задачи и каждого тега, затем атомарно заменяет связи.
4. При удалении `DELETE /api/tags/{id}` удаляется тег; связанные строки `task_tags` удаляются каскадно.

**Альтернативы:** повтор имени тега — `409`; чужой/несуществующий объект — `404` или `400` согласно операции.

### UC-07. Удаление задачи

**Основной актор:** авторизованный пользователь. **Предусловие:** задача принадлежит пользователю.

1. Пользователь подтверждает удаление.
2. Клиент отправляет `DELETE /api/tasks/{id}`.
3. Сервер удаляет только задачу текущего пользователя.
4. База данных каскадно удаляет строки `task_tags`; API возвращает `204 No Content`.

**Альтернатива:** задача не найдена или не принадлежит пользователю — `404`.

## План разработки и зависимости

| Этап | Работы | Зависимость | Результат |
|---|---|---|---|
| 1 | Анализ требований, use cases, ER-модель | Нет | Спецификация и модель данных |
| 2 | Создание схемы SQLite и ограничений | Этап 1 | Схема БД |
| 3 | Настройка Express, JWT и валидации | Этап 1 | Серверный каркас |
| 4 | Реализация API задач и тегов | Этапы 2–3 | Рабочие эндпоинты |
| 5 | Интеграция интерфейса с API | Этап 4 | Сквозные сценарии TaskFlow |
| 6 | Тесты, безопасность, OpenAPI и CI | Этапы 2–5 | Проверяемая версия MVP |

## Реестр рисков

| Риск | Последствие | Мера снижения |
|---|---|---|
| Изменение требований в ходе реализации | Переделки и срыв срока | Фиксация спецификации и обработка изменений отдельными задачами |
| Утечка паролей | Компрометация учётных записей | Хеширование bcrypt с солью; не возвращать password_hash |
| SQL-инъекция | Чтение или изменение данных | Параметризованные запросы better-sqlite3 и серверная валидация |
| Доступ к чужим данным (IDOR/BOLA) | Нарушение конфиденциальности | Проверка user_id в каждом запросе к пользовательскому ресурсу |
| Потеря локальной БД | Потеря задач и тегов | Резервное копирование и проверка восстановления |
| Регресс API | Поломка клиентских сценариев | Интеграционные тесты и CI при push/pull request |
